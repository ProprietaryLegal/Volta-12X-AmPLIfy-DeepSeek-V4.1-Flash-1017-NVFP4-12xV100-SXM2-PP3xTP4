## Summary

1. **New and largest: 1Cat #1482** (merged 2026-11-11, shipped in v1.5.3 on 11-14): DeepSeek-V4.1-Flash-1017 from the official checkpoint (FP8 dense, MXFP4 experts) on **PP4 x TP4, 16 V100s**. It is the first upstream pipeline of three or more stages for this model. Release table at 1K context, T=0: 1 request 19.3 ms/round (202 tok/s), 2 requests 396 tok/s in sum, 4 requests 628, 8 requests 888; 512K first read 132.7 s [R]. None of its switches is in ours (0 of 79 names) [R].
2. Its scheduling for many stages is a different design from our slots: **several requests per step** (`VLLM_V41_BATCH`), micro-batches that rotate through the stages (`VLLM_V41_PP_MICRO`), a request's next step queued while one is in flight (`VLLM_V41_PP_AHEAD`), and **one prompt chunk per stage in flight** (`VLLM_V41_PREFILL_PIPELINE`) [R]. Ours runs one request per step [R]. It has **no prefix cache**: "Native PP4 re-prefills every request" [R]; ours keeps prompts.
3. Our "NVFP4" experts are MXFP4 E8M0/32 records served on the skinny QPN path (`nvfp4_8r_native.py` docstring) [R], the same data format as #1482's `v41sk` expert kernels, so those kernels are candidates to port, not a different format [I].
4. **All-reduce for large sums: no upstream change reduces a large prompt-read sum in FP32 or replaces NCCL for it on this model** [R: dispatch chain of main]. Upstream precedents for the fix exist on another model: a tiled long-prefill path through the custom all-reduce for hidden size 5120, and a fused reduce-scatter + norm + all-gather [R].
5. **Port first** [I]: (a) #1482's prompt pipeline across stages and batched decode, as a study against our slot scheduler; (b) a sliced large-sum path modelled on main's tiled long-prefill reduce (question 2); (c) small fixes: #1537, #1502, #1362's idea, #1416; (d) #1482's expert kernels only after a per-layer timing comparison.
6. Fixes merged upstream since our base that touch pipeline serving: #1294, #1362, #1373, #1408, #1416, #1445, #1502; open and relevant: #1537, #1371, #1370, #1376 [R].
7. **Nothing new** since the last review in v100-skinny (last commit 2026-08-19), philbert440/deepseek-v4.1-v100 (main 23cec6a9, 2026-10-25) and 0rand (last push 2026-11-02, `main-0rand` a903cb5f) [R].
8. TensorFold / jayleaton (another engine, DGX Spark): session tier on NVMe, prompt checkpoints, a context window that adapts to the number of chats, and a fix that makes short prompts repeat exactly under replay prefill. Design references for the conversation store, not code to port [R/I].
9. Upstream vLLM: pipeline equivalence tests (#66291), a copy-engine hand-off between stages that is NVLink only (#65896), an FP32 residual truncated at a stage boundary (#65755), KV reuse across pipeline layouts (#67532) [R].
10. Not reached: the HTML report of #1482 ("shared separately"), the review-queue archives (#1448 to #1463) file by file, PR diffs line by line except where a file is cited, and upstream per-layer expert timings on our cards.

## Answers

**1. Three or more stages.** Upstream has it since 2026-11-11: #1482, four stages [R]. Scheduling: micro-batches and schedule-ahead with a per-request in-flight count (`_v41_inflight`), under **async** scheduling (`run_pp4.sh` passes `--async-scheduling`) [R]. Hand-off: rank-0-only send, deferred send, sampled tokens on their own NCCL communicator [R]. A request's next step waiting for its sampled tokens: main sets `next_decode_eligible_step = current_step + pp_size` only in `AsyncScheduler` and only for Model Runner V2 (`async_scheduler.py:59`) [R]; the sync scheduler of main does not set it, so our fix 9c6b310 has no upstream counterpart on the sync V1 path [R/I]. Generic fixes: bb03140e (#1371), #1373, #1294, vllm#54436 via #1408, open #1537 [R]. Peuqui serves GLM-5.3 at PP5 and found #1362, #1416 and #1502 there [R]. Tests: 1Cat `tests/models/test_deepseek_v41_pp_{commit,drafter,forward,split}.py`; vLLM #66291 [R]. APPLIES. In ours: only our own pieces. Port: the prompt pipeline is several files; batched decode is a redesign.

**2. All-reduce for large payloads.** Nothing upstream reduces a large V4.1 prompt-read sum in FP32 or in slices. Main's chain is ring, host-reduce, NCCL symmetric memory, quick-reduce, FlashInfer, custom, torch symmetric memory, then pynccl; a payload the custom path refuses ends in pynccl in the tensor's own dtype (`cuda_communicator.py:489-573`) [R]. #1482's `LL_AR` stops at 1 MiB [R]. #1284 documents that V4.1 sums of 4,194,304 or more elements (820 rows of 5,120) go through pynccl in place [R]. Two precedents to copy: `_try_tiled_long_prefill_gemma_rms_norm` cuts a long prompt's rows into tiles that fit the custom path's `max_size` (hidden 5120, FP16 input, FP32 residual), and the fused reduce-scatter + norm + all-gather of #1524 [R]; both are bound to Qwen's norm. mzen17's profile names the NCCL kernel (`AllReduce_Sum_f16_RING_LL`) [R]; a ring adds in an order set by where a chunk starts on the ring, which fits the local finding that rounding moves with buffer size and offset [I]. APPLIES. Not in ours (tiled function 0 hits) [R]. Port: several files; the custom path reduces in rank order, so a sliced sum would be the same for every chunk cut [I]. Read-speed cost unknown.

**3. Prompt-read kernels.** The 8,188-row gate is ours alone (`prefill_dense_blas.py:25`, `dense_tm.py:502`); upstream has no 8,188 anywhere [R]. Upstream's long-chunk switches on the native path: `VLLM_V41_DEQUANT_MM_ROWS` (FP8 layers dequantize and use a GEMM from 64 rows), `VLLM_V41_HC_GEMM`, `VLLM_V41_HC_PARTS_CUDA`, `VLLM_V41_INDEX_SHARD`, `VLLM_V41_ATTN_RING_PREFILL`, `VLLM_V41_PREFILL_PIPELINE`; chunk size 4,096 in the release configuration [R]. Its figures: 14,253 tokens first token 2.93 to 2.95 s; 512K 130.9 to 132.7 s (about 3,900 tok/s) on four stages [R]. Skipping late layers on early chunks is our #1376 (open upstream) [R]. Chunk size by prompt length: #1416 [R]. APPLIES: the prompt pipeline and #1416; the FP8 dense kernels DO NOT APPLY to GGUF dense.

**4. Expert kernels and loading.** v100-skinny unchanged [R]. 1Cat since our base: #1518 (QPN2 9 to 64 rows), #1544 (raw 1-byte scales, repeated-expert loads), #1482's `v41sk` (fused W13 + SwiGLU, route match, double-buffered MoE, w2 route) [R]. Ours already has a group plan, SwiGLU kernel and route plan [R]; whether upstream's are faster on six rows is UNKNOWN until both are timed per layer. Load: #1319 (in ours), #1362 (own version), #1020 and #1145 (GGUF loading, in base) [R/I]. Expert tables in card memory: #1544's saving does not apply (1-byte scales already) [R].

**5. Slots, first token, kept prompts, store.** Upstream concurrency is batched decode: 4 requests cost 24.8 ms per round against 19.3 for one [R]; ours time-slices one request per step and measured three together at 288 tok/s against 129.5 for one [R: the build's record]. Upstream native has no prefix cache and no session store [R]. Kept prompts on the #1277 path: session prefix stops hitting above 524,288 tokens (issue #1523, open, no cause) [R]; hot-ring refill #1381 is ours. KV retention work (#1444, #1466, #1476, #1486) is for the vLLM block pool, which V4.1's packed KV does not use [I]. Store ideas: jayleaton's NVMe session tier and prompt checkpoints; TensorFold #2128's arithmetic policy in the saved state's identity (a record read with another chunk cut is another rounding) [R/I]; vLLM #67532's layer-range keys [R].

**6. Warm-up and load.** Upstream's V4.1 native path has no warm-up of its own beyond a client's first requests (`cluster/bench.sh`) [R]. Generic: #1402 lists what a warm-up must reach (every request count, a mixed step, a full chunk) but is for Model Runner V2; #1394 and issue #1326 show the cause of compiles on first requests (integer arguments specialised on value) and the cure (`do_not_specialize`); #1518 pre-warms sampling kernels at speculator load; #1502 returns the memory a cold compile takes; issue #1423: a compile cache under `/tmp` is lost on restart [R]. APPLIES as a checklist: warm one request per slot count, one full 4,096-row chunk, one odd tail length, and T>0 sampling [I].

**7. Take or avoid.** Take: the per-stage memory snapshot and step trace of #1482 (`VLLM_V41_MEMSNAP_DIR`, `VLLM_V41_TRACE`) for windows; a PP3-against-PP2 equivalence test in the manner of vLLM #66291; a read of our hand-off buffer's dtype (vLLM #65755). Avoid: `VLLM_V41_PP_RECV_EARLY` (shipped off, illegal access); `fp8_e5m2` KV (mzen17: mean KL 0.23 nats); comparing our speed with #1482's table without its conditions: 16 cards, four nodes on InfiniBand, memory clock 1,053 MHz per the v1.5.3 notes (stock 877), greedy, 1K context [R].
